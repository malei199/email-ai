# 时间线推理微调数据集构造方案

> 目标：基于 `email_events` 知识库中的 4668 个真实事件，构造 300+ 条高质量的"时间线推理与根因分析"微调数据。

---

## 一、总体设计思路

### 1.1 为什么需要专门构造这类数据？

现有通用 LLM（如 DeepSeek-V3）虽然能读懂邮件内容，但**缺乏以下能力**：
- 稳定输出**结构化 Markdown 表格**
- 识别"计划日期 vs 实际日期"的**对比推理**
- 基于多阶段事件链条进行**根因归因**
- 对缺失数据给出**"未找到记录"的诚实提示**

因此需要构造专门的 SFT 数据，让模型学习"基于事件列表 → 整理表格 → 分析根因"的固定模式。

### 1.2 构造策略

```
4668 个真实事件
    │
    ▼
筛选 80~100 个种子款号（事件数 5~15，覆盖多阶段，含延期）
    │
    ▼
人工/规则构造 80~100 个标准 QA 对（黄金样本）
    │
    ▼
LLM 数据增强（改写提问方式 × 3~4 种变体）
    │
    ▼
320~400 条训练数据（ChatML 格式）
    │
    ▼
人工抽检 20% → 修正 → 最终 300+ 条可用数据
```

### 1.3 数据量级估算

| 阶段 | 数量 | 说明 |
|------|------|------|
| 种子款号 | 80~100 个 | 事件数 5~15，覆盖主要 category |
| 黄金 QA 对 | 80~100 条 | 基于真实事件直接构造 |
| LLM 增强变体 | × 3~4 | 同一款号的不同问法、不同侧重点 |
| 去重过滤后 | ~350 条 | 去除重复模式和质量不合格的 |
| 人工抽检修正后 | **300+ 条** | 最终训练集 |

## 二、种子款号筛选策略

### 2.1 筛选规则

从 `events_passed.json` 的 965 个款号中自动筛选：

```python
SELECTION_CRITERIA = {
    "min_events": 4,        # 至少 4 个事件（能讲出故事线）
    "max_events": 20,       # 最多 20 个事件（避免 Prompt 过长）
    "exclude_unknown": True,# 排除 style_id == "UNKNOWN" 或空
    "required_categories": ["样衣", "面料", "出货"],  # 优先覆盖核心阶段
    "delay_preferred": True,# 优先选择有 delay_days > 0 的款号
    "date_valid_ratio": 0.7,# 至少 70% 的事件有有效日期
}
```

### 2.2 分类覆盖目标

确保筛选出的种子款号能覆盖以下场景：

| 场景类型 | 目标占比 | 说明 |
|---------|---------|------|
| **全流程款号** | 30% | 包含 Lab Dip → 样衣 → 大货样 → 出货的完整链条 |
| **延期根因款号** | 40% | 包含明显的 delay_days > 0，且涉及多个阶段的连锁延期 |
| **单一阶段深入款号** | 20% | 如只有"样衣"阶段，但有多次修改/批复/给意见 |
| **信息缺失款号** | 10% | 某几个阶段完全无记录，训练模型诚实回答"未找到" |

## 三、黄金 QA 对构造规则

### 3.1 输入格式（User Prompt）

统一采用"**事件列表 + 问题**"的格式：

```markdown
款号: AW25-KFWTS101

事件记录：
[事件1] 样衣 | 工厂提交 | 2025-07-09 | 工厂 → 客人 | 样衣于 7/9 寄出
[事件2] 出货 | 延期申请 | 2025-07-09 | 工厂 → 客人 | 请求周五拖车，避免延到下周
[事件3] 一般沟通 | 给意见 | 2025-07-09 | 客人 → 工厂 | 拉链尺寸表已发送

请根据以上事件记录，整理成时间线表格并分析延期根因。
```

### 3.2 输出格式（Assistant 标准答案）

强制要求 Markdown 表格结构：

```markdown
## AW25-KFWTS101 时间线梳理与延期根因分析

### 面料部分
| 阶段 | 事件 | 实际时间 | 计划时间 | 延期 | 备注 |
|------|------|---------|---------|------|------|
| - | - | 未找到记录 | - | - | - |

### 样衣部分
| 阶段 | 事件 | 实际时间 | 计划时间 | 延期 | 备注 |
|------|------|---------|---------|------|------|
| 样衣 | 工厂提交 | 2025-07-09 | - | - | 7/9 寄出 |
| 一般沟通 | 给意见 | 2025-07-09 | - | - | 拉链尺寸表 |

### 出货部分
| 阶段 | 事件 | 实际时间 | 计划时间 | 延期 | 备注 |
|------|------|---------|---------|------|------|
| 出货 | 延期申请 | 2025-07-09 | - | +3天 | 请求延后拖车 |

### 根因结论
...
```

### 3.3 人工构造的三种问法模板

同一款号至少构造 3 种不同侧重点的问题：

1. **通用时间线查询**
   > "款号 {style_id}，帮我查一下现在到哪个阶段了？"

2. **延期根因查询**
   > "款号 {style_id} 工厂要求延期，帮我查一下是哪个环节延期导致的？"

3. **特定阶段查询**
   > "款号 {style_id} 的样衣阶段有什么反馈？"（只聚焦于 `category == "样衣"` 的事件）

4. **对比查询**（只选有明显 related_date 的款号）
   > "款号 {style_id} 的实际进度和计划进度有什么偏差？"

## 四、LLM 数据增强策略

### 4.1 增强维度

对每一个黄金 QA 对，用 DeepSeek API 生成 **3~4 个变体**：

| 增强维度 | 示例 | 目标 |
|---------|------|------|
| **提问方式改写** | "查一下进度" → "现在到什么阶段了？" → "进度怎么样了？" | 让模型适应不同口语化表达 |
| **阶段聚焦改写** | 通用查询 → "面料部分怎么样了？" | 训练模型只输出特定阶段 |
| **上下文截断** | 从完整事件列表中随机移除 1~2 个非核心事件 | 训练模型基于不完整信息做合理推断 |
| **日期缺失模拟** | 将某些事件的 date 替换为 "未明确" | 训练模型处理信息缺失 |
| **人称变化** | "帮我查" → "请分析" → "这个款号延期了吗？" | 增强对指令风格的泛化 |

### 4.2 增强 Prompt 示例

```
你是一位数据增强专家。请基于以下原始问答对，生成 3 个语义等价但表达方式不同的变体。

要求：
1. 保持 Assistant 的答案不变（只改 User 的提问和事件列表描述方式）
2. 变体 1：口语化改写提问方式
3. 变体 2：聚焦于特定阶段的提问（如"面料部分"、"样衣部分"）
4. 变体 3：上下文截断版本（随机隐藏 1 个非关键事件）

原始问答对：
{原始 JSON}

请输出 JSON 数组，每个元素包含 "messages"（ChatML 格式）。
```

### 4.3 增强后质量控制

- **答案一致性校验**：所有变体的 `assistant` 内容必须相同
- **事件覆盖率校验**：确保变体中没有隐藏关键延期事件（否则答案就错了）
- **去重**：基于 user prompt 的 MD5 去重

## 五、数据格式与输出

### 5.1 ChatML 格式

```json
{
  "messages": [
    {
      "role": "system",
      "content": "你是服装行业业务分析师。请根据提供的事件记录，整理成结构化时间线表格并分析延期根因。如果某阶段无记录，请明确标注'未找到记录'，不要编造。输出必须使用 Markdown 表格。"
    },
    {
      "role": "user",
      "content": "款号: AW25-KFWTS101\n\n事件记录：\n[事件1] ...\n\n请根据以上事件记录，整理成时间线表格并分析延期根因。"
    },
    {
      "role": "assistant",
      "content": "## AW25-KFWTS101 时间线梳理..."
    }
  ]
}
```

### 5.2 输出文件

| 文件 | 说明 |
|------|------|
| `datasets/timeline_gold_samples.jsonl` | 80~100 条人工/规则构造的黄金样本 |
| `datasets/timeline_augmented.jsonl` | LLM 增强后的 300+ 条数据 |
| `datasets/timeline_train.jsonl` | 最终训练集（去重+过滤后） |
| `datasets/timeline_dataset_stats.json` | 统计报告：总数、分类覆盖、增强比例等 |

## 六、落地执行计划

### Step 1：自动筛选种子款号（5 分钟）
运行脚本自动从 `events_passed.json` 中筛选出 80~100 个符合标准的种子款号。

### Step 2：生成黄金 QA 对（15 分钟）
脚本自动基于种子款号的事件聚合结果，生成 3 种基础问法的黄金 QA 对。

### Step 3：LLM 数据增强（30~60 分钟）
调用 DeepSeek API 对每个黄金样本做 3~4 个变体生成。预计费用 **5~15 元**。

### Step 4：后处理与过滤（10 分钟）
运行脚本进行去重、长度过滤、答案一致性校验。

### Step 5：人工抽检（30~60 分钟）
随机抽取 50 条数据人工检查，修正明显的格式错误或事实错误。

### Step 6：格式转换（5 分钟）
转换为 ChatML / ShareGPT 格式，供 LLaMA-Factory 使用。

**总计耗时：约 2~3 小时（含 API 等待时间）**

## 七、与 LLaMA-Factory 的对接

构造好的 `datasets/timeline_train.jsonl` 可直接用于 LLaMA-Factory：

```yaml
# dataset_info.json
{
  "timeline_reasoning": {
    "file_name": "datasets/timeline_train.jsonl",
    "formatting": "sharegpt",
    "columns": {
      "messages": "messages"
    }
  }
}
```

训练配置建议使用 **LoRA**，重点参数：
- `learning_rate: 5e-5`
- `num_train_epochs: 3`
- `template: qwen`（或其他你用的 base 模型模板）
- `cutoff_len: 4096`（时间线 Prompt 可能较长）

## 八、关键风险与规避

| 风险 | 影响 | 规避措施 |
|------|------|---------|
| 黄金样本答案质量不高 | 增强后的数据全部被污染 | 先做 10 条人工验证，确认模板正确后再批量生成 |
| LLM 增强时修改了答案 | 事实错误 | 强制 Prompt 要求 "Assistant 答案必须一字不差" |
| 事件列表过长超出 cutoff | 训练时被截断 | max_events 限制为 20，cutoff_len 设为 4096 |
| UNKNOWN 款号污染数据 | style_id 不明确，答案不可靠 | 严格过滤 style_id == "UNKNOWN" |
| 日期格式混乱 | 模型学不会时间排序 | 预处理阶段统一清洗日期格式 |
